## 比赛诊断日志

按原方式 `bash SDK_Python/run.sh <port>` 启动即可。SDK 默认使用
`print(..., flush=True)` 输出日志，由比赛平台收集，不写日志文件、不额外打包。
赛后直接复制平台上的精简 `HUNTER` 日志即可。

默认是适合复制粘贴的 `compact` 模式：每行以 `HUNTER ` 开头，后面是独立JSON，
`schema=2`。启动一行、首个回合一行，之后每20个有效回合一条摘要；
每20回合最多另输出两条关键变化，首个程序异常另有一条保留名额。
重复失败合并计数，成功POST不再逐次打印访问记录。

摘要保留金币、积分、基地血量、角色位置、动作短描述、任务进展和失败原因；
失败动作附前次目标与起点，攻击失败附控制距离/射程/冷却检查，判题错误与动作受理分开。
完整地图、商店、模型输入输出、沙盒正文与长堆栈默认收起；日志过长时优先保留问题和计数。
复制启动行及问题附近的 `HUNTER` 行和下一条摘要即可，不需要上传文件。

LLM 诊断版本在启动行显示 `task_diag=2`。正常每题保留3条 `llm`、2条 `task_exec`；
不同拒绝原因、检查器完成、TOKEN 和 HTTP 错误另有有界名额，重复情况合并计数。
`llm` 保留确切拒绝原因、证据ID/提取路径、SDK要求的检查器和实际退出码；
`task_exec` 保留输出结构、TOKEN数量/摘要，以及本地 urllib 请求的认证头名称和认证方式。
相关文档仅记录几行脱敏短句（`task_context`），提交和结束各有 `task_submit`、`task_end`。
实际提交不代表判题通过。复制同一 `task` 的这些行即可定位自进化失败，无需打开full模式。

### 自进化协议与一次启动准备

模型只需复制当前 `request_id`，返回 `{"request_id":"...","cmd":"Python源码","cwd":"ws_2"}`
或 `{"request_id":"...","submit":{"token":"实际结果"}}`。`cwd` 可省略，默认为任务根目录。
需要补读文件时使用 `cmd:{"read":"实际路径","offset":0}`，列目录使用 `cmd:{"list":"."}`。
SDK补齐内部计划和证据引用；失败或不完整执行不能用于提交，旧请求编号不能串入新任务。
临近截止时间只允许submit，模板与接收校验一致。旧协议继续兼容已有调用。

新任务首次 `executeCmd` 同时探测Python/当前目录、定位任务文件、读取目录和相关题目/API/spec文档，
各文档继续逐块校验哈希。普通小任务一次返回后即可请求模型执行；超出文档或目录预算时明确回退分页，
缺失或歧义题目不猜选。所有工具仍在比赛沙盒跨回合执行，不在HTTP回调里执行。

日志不改变 HTTP 响应的三个字段。打印失败不会使本来合法的动作失败。
若下一场需要完整采集，启动前设置 `HUNTER_LOG_MODE=full`，恢复原有
`schema=1`、`run/seq`、`part/parts`、`payload` 分段格式。省略的正文无法从精简摘要恢复。
详见工作区 [日志说明](../../docs/SDK_LOGGING.md)。

### 同目标移动的单方让行

多个角色首选同一个空格时，按稳定角色 ID 顺序只允许一方通行，其余角色当回合不发移动指令，避免双方同时横移、改道再相撞。已有候选解和备用候选也执行同一限制。实际观察到先行者通过后，后方角色按新的占用地图继续走，不假设发送移动即成功。

若上一回合出现同目标移动且两方明确失败、实际位置均未变，只让优先方重试，另一方等待。优先方随后单独失败仍执行原有障碍退避；缺失反馈或跨回合跳帧不推断碰撞。该机制与守炮、门口的专用让行约束共同生效。

### 回防工人采购兜底

晚前采购优先开拓者；开拓者忙于任务/寻宝、背包无空间或采购回防路线不够时间时，可由有完整商店→实际防守站位路线的回防工人接管。兜底按至少一次购买和回程余量逐回合核验，不招回夜间外勤，也不打断施工、封门重试、让行或已有升级券配送。采购物品进入工人自己的背包，按工人炮位可用目标选择升级券/修墙包及自用消耗品。保留已规划寻宝的祭品经费及金币底线，允许开拓者继续执行其寻宝购买。日志market标注fallback_worker与实际买家。
